## 1. 评审结论（先看这个）

**需求应当收敛，而不是整体新建一个"AI 模块"。**

六项诉求中：

- **3 项已具备存储与字段，不需要模型**（主色卡、标签、自然语言描述）
- **2 项是同一个模型的两个方向**（相似照片查找 + 文本描述查找照片）
- **2 项可选依赖第二个模型，可后置**（图片描述、标签自动建议）

因此实际新增模型数为 **1 个必需（CLIP 系 embedding）+ 1 个可选（VLM caption）**，而非需求字面暗示的一整套模型。

> ⚠️ 附带发现：`DESIGN.md` 已严重过期（仍描述 PostgreSQL + GORM + `prominentcolor` 的方案），实际架构已演进为本地 SQLite 库。本文档的一切结论以 `local_library/` 下真实代码为准。建议单独安排一次 DESIGN.md 的修订。

## 3. 需求收敛详解

### 3.1 为什么"相似照片"和"文本搜图"是一个模型

CLIP 系（含 SigLIP / MobileCLIP）是**图文对比学习**模型，图像编码器与文本编码器输出到同一个对齐的向量空间。因此：

- 为每张图片算一次 image embedding 并持久化
- 图查图：用某张图的向量做查询向量
- 文查图：用文本编码器把 query 编码成同维度向量

两者是同一份数据上的两种查询，**不需要两个模型，也不需要做两次索引**。这是本次评审最重要的收敛点。

### 3.2 主色卡：问题真实存在，但模型不是解药

> 用户反馈："提取出来的颜色并未涉及到照片主题色，反而把图片中的暗部颜色给提取出来了。"
> **该反馈经实测确认成立，且严重程度高于预期。** 完整实验见 **附录 A**。

> ✅ **本节方案已落地（2026-09-16）**，实现见 `local_library/media.go`。与下方初版设想有三处偏差，均以实测为准：
> 1. 暗部门槛由 `L < 18` 上调为 **`L < 25`**——18 时暗绿叶子仍会挤在主体黄花**之前**（见附录 A 实测对比），25 时四场景命中 8/8、暗色占位 0。
> 2. 兜底方式由"回退旧算法"改为 **逐级放宽的 4 级通道**（25/95/8 → 8/98/3 → 不过滤 → 不过滤且忽略 alpha），保证任何图都出得来色卡。
> 3. 迁移风险已随实现一并解决：新增 `assets.dominant_colors_version` 列（默认 0），按版本触发一次性重算。
>
> **性能**：40k 采样点（最大样本量）下新算法 **1.17 ms/张**，旧算法 **1.90 ms/张**——新版反而快约 38%。
> 主要来自两点优化：`math.Cbrt` 换成 8192 级查找表（Go 的 Cbrt 是软件实现，每像素 3 次，原占 ~40% 耗时），以及每像素由 `At()` + `NRGBAModel.Convert()` 两次接口调用合并为一次 `At().RGBA()`。

**实测数据（4 个典型场景，每张色卡 5 格，共 20 格）**

| 指标 | 现有算法 | 零模型改进方案 |
|---|---|---|
| 主题色命中率 | 4/8（50%） | **8/8（100%）** |
| 暗色/灰色占位 | **15/20** | 2/20 |
| 色卡内视觉重复对 | **21 对** | 0 对 |

夜景场景最极端：现有算法返回的 5 个颜色全部是近黑蓝（`#060B16` `#0C1426` `#121929` `#182338` `#131D32`），主题色命中 0，色卡内出现 8 对重复颜色——**色卡完全失去信息量**。

**根因（两处缺陷，均在 `local_library/media.go:601`）**

1. **完全没有暗部过滤**。现有过滤条件只有 `pixel.A < 125`（透明）与 `pixel.R > 250 && pixel.G > 250 && pixel.B > 250`（近白）。**近黑像素被完整保留**，这是"暗部被提取"的直接原因。
2. **排序准则错误**：按像素**数量**降序。照片中暗部/背景通常占据最大面积；而真实照片的暗部因渐变与传感器噪声，会在 4bit 分桶下**分裂成大量相邻桶**，每个桶的计数仍然高于小面积的主体色。合成纯色图看不出这个问题，一旦加入渐变与噪声，暗部立刻霸占整个色卡。

**为什么不该用 CLIP / embedding 模型**

CLIP 系模型的输出是**语义向量**——它能表达"这是一张夜景"，但**不包含、也无法反解出颜色值**。用 CLIP 提取主色在概念上不成立，这是模型能力与需求的错配。

**唯一可能帮上忙的模型是显著性/语义分割（Saliency / Segmentation）**，它回答的是"主体在哪"，而不是"主体什么颜色"。但：

- 它只解决**空间定位**，取色仍然必须回到颜色聚类算法
- 实测表明"暗部过滤 + 饱和度加权"已能覆盖主体偏心场景（附录 A 案例 4，命中 2/2），中心先验只是辅助项
- 引入模型的代价（运行时分发、体积、启动开销、许可）与收益不成比例

**VLM 直接问颜色同样不可取**：输出是"深蓝色"这类语言描述而非精确色值，不可复现、每张耗时数百毫秒到秒级，且需要引入完整 VLM 栈。

**正确解法（零模型，四步）**

1. **转 CIELAB** 做聚类（感知均匀，避免 RGB 空间的距离失真）
2. **过滤无效像素**：排除极暗（**L < 25**，落地值；初版设想 18 经实测偏低）、极亮（L > 95）、低饱和（chroma < 8）
3. **加权排序**替代纯计数：权重 = 面积 × 饱和度 × 中心先验，让视觉显著的颜色胜出
4. **ΔE 去重**：候选间 ΔE76 < 12 视为同一色，保证色卡内颜色彼此可区分

四步都在纯 Go 内完成，无新增依赖、无模型、无运行时。

✅ **迁移风险已解决**：新增 `assets.dominant_colors_version INTEGER NOT NULL DEFAULT 0`，旧行读为 0。`reconcile.go` 的重算条件加入 `staleColors`（**已有色卡且版本落后**），`pendingThumbnailAssets` 同步加入版本条件触发 warming 回填。

关键防护：该条件**只匹配已有色卡的资产**，与既有的 `DominantColors == "[]"` 缺失重算逻辑互不重叠——否则永远取不到色的资产（如部分视频）会被每次扫描重复排队。已有两个测试守着这条边界（`store_dominant_colors_test.go`）。

**残留局限（应如实告知）**：当主体本身就是低饱和或极暗色（如雾天、煤矿、纯黑白摄影）时，饱和度/亮度过滤会连主体一起滤掉。✅ 已按建议实现**逐级放宽兜底**：主通道取不到色时依次放宽到 `L ∈ [8,98] / chroma ≥ 3`、`L ∈ [0,101] / chroma ≥ 0`、最后连 alpha 也不过滤。

ℹ️ 副作用：色卡会变**短**（典型 2~3 个色而非固定 5 个），因为 ΔE 去重与主通道过滤会剔除"同一个背景的五个深浅变体"。前端 `LibraryColorStrip` 用 `flex-1` 平铺，色块自动变宽，不会破版。

### 3.3 标签与描述的"自动"语义需澄清

需求中"为照片添加标签或自然语言的描述"存在两种解读，工作量差异极大：

- **(a) 用户手动添加** → **现已支持**，无需开发
- **(b) 模型生成候选，用户确认采纳** → 需要 VLM caption，且**必须区分来源**

若走 (b)，数据模型必须区分人工与 AI 产出，否则用户手动标签会被 AI 覆盖。建议 `asset_tags` 增加 `source` 列（`manual` / `ai`），或独立 `ai_suggested_tags` 表。同理，AI 生成的描述建议写入独立字段（如 `ai_caption`），与用户 `notes` 分离，避免污染用户数据。

## 4. 技术方案建议

### 4.1 集成形态：sidecar 进程（推荐）

新增 `emulsion-inference` sidecar，主进程通过 **JSON-RPC over stdio** 调用（复用 `agent_extensions/mcp.go` 既有模式）。

**为什么不选其他方案：**

| 方案 | 否决理由 |
|---|---|
| CGO 静态链接 ONNX Runtime | 破坏当前零 CGO 状态；交叉编译与 Windows 打包成本陡增；`wails.json` 已有 `build:tags: nodynamic`，方向是减少动态依赖 |
| 纯 Go 重写推理 | 不现实，生态缺失 |
| 内嵌 Python runtime | 体积大，且项目**已有 Node runtime 管道**，无需再引入第二套运行时 |
| 直接调云端 API | 与"本地库 + 离线可用"定位冲突，且图片需上传，隐私与成本均不可接受 |

**为什么选 Node sidecar：**

- 项目**已在下载并打包 Node runtime**（插件宿主用），管道现成，零新增运行时
- `onnxruntime-node` / `transformers.js` 生态成熟，tokenizer、图像预处理、自回归解码都不必自己写
- 进程隔离：模型或推理库崩溃不会拖垮主程序
- 模型文件不进安装包，按需下载，安装包体积不受影响

**生命周期**：懒启动（首次调用时拉起）+ 空闲超时退出，避免常驻占内存。

### 4.2 模型选型

**必需：embedding 模型（首版只上这一个）**

| 候选 | 体量（FP16 ONNX） | 维度 | 特点 | 建议 |
|---|---|---|---|---|
| **MobileCLIP2-S2/B** | 约 32–80MB | 512/640 | 为端侧设计，CPU 上最快 | ⭐ 首版默认 |
| **SigLIP-B/16-256-multilingual** | 约 280MB | 768 | 精度更高，多语言（中文 query 关键） | ⭐ 中文场景强烈建议 |
| CLIP ViT-B/32 | 约 150MB | 512 | 生态最全但精度已落后 | 备选 |

> 中文文本搜图是刚需，而标准 CLIP 的 text encoder 对中文支持弱。**建议优先评估 SigLIP 的 multilingual 变体**，否则"海边日落"这类中文 query 的召回会明显劣化。这一条需要实测，不能只看英文 benchmark。

**可选：caption / VLM（建议后置）**

| 候选 | 体量 | 许可 | 建议 |
|---|---|---|---|
| Florence-2-base | 约 230M 参数 | MIT | 首选，任务统一、体积小 |
| Moondream 0.5B / 2B | 0.5–1.9B | Apache-2.0 | 备选 |
| SmolVLM2 256M / 2.2B | 0.25–2.2B | Apache-2.0 | 备选，需自回归解码，较慢 |

VLM 自回归生成比 embedding 慢一个量级（每张数百 ms 到秒级），且引入 tokenizer + KV cache 复杂度。**建议首版不做**，等 embedding 链路跑通后再加。

### 4.3 向量存储：sqlite-vec

- 引入 `modernc.org/sqlite/vec`（纯 Go、零 CGO、blank import 即可注册），与现有 `modernc.org/sqlite` 无缝，无需更换驱动。
- 建 `vec0` 虚拟表存 embedding，KNN 查询用 `vec_distance_cosine`。

**规模与性能判断（重要）：**

| 库规模 | 512 维 float32 体积 | 暴力 KNN 耗时估计 |
|---|---|---|
| 1 万张 | 约 20MB | 十毫秒级 |
| 10 万张 | 约 200MB | 百毫秒级 |

本地相册规模通常在几千到几万张，**远未达到需要 ANN 索引的百万级阈值**。因此：

> ✅ 结论：**不需要 HNSW / IVF 等近似索引**，用 sqlite-vec 的暴力 KNN 即可。不要在这一版做 ANN，属于过度设计。

⚠️ 风险：sqlite-vec 目前仍是 **pre-v1（v0.1.10-alpha.4）**，API 存在破坏性变更风险。建议薄封装一层数据访问，便于替换。

### 4.4 数据模型变更建议

```
assets
  + dominant_colors_version   INTEGER   -- 色卡算法版本，驱动 backfill
  + ai_caption                TEXT      -- AI 生成描述，与 notes 分离
  + embedding_status          TEXT      -- pending / ready / failed / skipped
  + embedding_model           TEXT      -- 记录模型标识，便于换模型后重算

asset_tags
  + source                    TEXT      -- manual / ai

新增 vec0 虚拟表：asset_embeddings(asset_id, embedding float[N])
```

`embedding_model` 列是必要的：更换 embedding 模型后旧向量**不可与新模型混用**，必须能识别并全量重算。

### 4.5 检索入口设计

建议**混合检索**，而非纯向量：

1. 用户输入 query
2. FTS5 走关键词分支（精确命中文件名、标签、notes）
3. 向量走语义分支
4. 两路结果融合排序返回

理由：纯向量检索会丢失"精确匹配文件名"这类确定性结果，而 FTS5 已存在且成熟。

## 5. 风险清单

| # | 风险 | 影响 | 缓解建议 |
|---|---|---|---|
| 1 | **中文语义检索效果不确定** | 高。CLIP 系英文强、中文弱，直接决定功能成败 | 首版前必须做中文 query 实测；优先 multilingual 变体 |
| 2 | **模型分发**：几百 MB，且国内访问 HuggingFace 不稳定 | 高 | 自建 CDN / 镜像；下载需进度 + 断点续传 + 校验 |
| 3 | **首次索引耗时**：1 万张 × 约 20ms ≈ 3.5 分钟 | 中 | 复用扫描管线进度事件；后台任务；支持中断续跑 |
| 4 | **杀软干扰**：下载的模型与 runtime 可能被实时扫描拦截（本机存在 `rename` EPERM 前例） | 中 | 下载落临时目录后校验再改名；引导用户加白名单 |
| 5 | **sqlite-vec 为 pre-v1** | 中 | 薄封装隔离；锁定版本 |
| 6 | **模型许可证**：分发前需逐个确认 | 中 | SigLIP(Apache-2.0) / Florence-2(MIT) / SmolVLM(Apache-2.0) 较友好；MobileCLIP 为 Apple 释出，需确认具体条款 |
| 7 | **跨平台**：`wails.json` 目前只配了 Windows NSIS | 中 | 若 macOS/Linux 也要发布，sidecar 需三平台打包 |
| 8 | **隐私承诺**：若 caption 改走云端即违背本地化承诺 | 中 | 明确写入产品说明：所有推理在本地完成 |
| 9 | 主色算法变更需全库 backfill | 低 | 版本号列驱动，随扫描渐进完成 |

## 6. 分阶段建议

**Phase 1 — 打通向量链路（核心，建议首版）**
- `emulsion-inference` sidecar（Node + ONNX Runtime），stdio JSON-RPC
- 引入 sqlite-vec，建 `asset_embeddings`
- embedding 批处理接入现有扫描管线（进度 / 中断 / 去重）
- 文本搜图 + 相似照片两个入口
- 模型按需下载与版本管理

**Phase 2 — 检索体验**
- FTS5 + 向量混合检索与结果融合排序
- 相似照片的阈值可调、批量去重建议

**Phase 3 — 生成能力（VLM，可后置）**
- 图片描述生成，写入 `ai_caption`
- 标签自动建议，带 `source=ai` 标记，需用户确认

**Phase 4 — 主色算法升级（可与上并行，零模型）**
- 转 CIELAB + ΔE 去重
- 版本号驱动 backfill

## 7. 待拍板问题（需要产品/技术决策）

1. **中文优先还是英文优先？** 这决定 embedding 模型选型，必须在开发前实测确认。
2. **作用范围是本地库，还是也覆盖云端库？** 云端库数据在 PostgreSQL（mo-gallery-web 仓库），本地推理需要原图；若需覆盖云端库，要设计服务端 embedding 方案，工作量量级不同。
3. **"添加标签/描述"是手动（已支持）还是 AI 建议？** 若是后者，需确认 AI 产出与人工数据的隔离规则。
4. **首版是否接受引入 Node runtime 依赖？** 若目标机器不愿额外下载 Node，需改用其他形态（如 Rust/C++ 编译的独立推理二进制）。
5. **模型是否随安装包分发？** 建议不随包分发（按需下载），需确认离线场景与首次体验的取舍。

## 附录 A：主色算法实证（2026-09-16）

### A.1 实验方法

用合成图复现两类算法并对比。实验脚本与对比图：

- 脚本：`color_probe.py`（本目录）
- 对比图：`color-algorithm-compare.png`（本目录）

合成图刻意还原真实照片的两个特征，这是暴露问题的关键：

1. **暗部是连续渐变 + 噪声**，而非单一纯色（真实传感器的必然结果）
2. **主体面积远小于背景**（符合绝大多数摄影构图）

> 用单一纯色合成图做测试会**严重低估**问题：纯色暗部只占 1 个桶，看似无害。一旦引入渐变与噪声，暗部会分裂成大量相邻桶，这才是"暗部霸占色卡"的完整机理。

### A.3 改进算法的参数（实测取值）

**落地后的最终取值**（Go 实现 `local_library/media.go`，与下表略有出入）

| 参数 | 取值 | 作用 |
|---|---|---|
| 主通道 `minL` / `maxL` / `minChroma` | **25** / 95 / 8 | 滤除暗部（核心修复）、高光溢出、低饱和灰 |
| 兜底通道 2 | 8 / 98 / 3 | 低饱和照片（黑白、雾景） |
| 兜底通道 3 | 0 / 101 / 0 | 极暗照片；上限取 101 是因为纯白的 L\* 实测为 100.0000039 |
| 兜底通道 4 | 同 3 + 忽略 alpha | 全透明图的最后出口，避免空色卡导致无限重排队 |
| 中心先验 `centerBonus` | 1.6 | 轻量近似"主体在中心"的构图先验 |
| 去重阈值 ΔE76 | < 12 | 色卡内最小可区分度 |

权重公式：`weight = (1 + 1.6 × (1 − 归一化中心距)) × (0.25 + chroma / 60)`（面积隐含在内：每个采样像素各贡献一次）

**为什么 `dark_l` 从 18 提到 25**（Go 侧实测，四个场景）

| 场景 | `minL=18` | `minL=25` |
|---|---|---|
| 夜景城市 | `#f7ca4a #e8813a` **`#202c45`**（混入暗蓝） | `#f7ca4a #e8813a` |
| 暗调人像 | `#b03737 #d69e80` | `#b03737 #d69e80` |
| 暗叶红花 | `#c4262c` **`#1c3926`** `#f4c450`（暗叶插队到主体黄花前） | `#c4262c #f4c450 #284634` |
| 偏心主体 | `#40c4d0 #e86048` | `#40c4d0 #e86048` |

阈值 18 时 L\*=18.1 的暗蓝、L\*=21.3 的暗绿都能"擦线"通过，其中暗绿甚至排在小面积主体黄花**之前**。提到 25 后四场景均为「暗色占位 0、重复对 0、主题色命中 8/8」。L\*=25 约等于 sRGB 灰 `#3D3D3D`，作为"阴影地板"是合理的量级。

### A.4 关于"偏心主体"这个边界

案例 4 专门检验中心先验的失效边界：主体被刻意放在左下角、背景占 86%。结果改进算法仍命中 2/2。

**结论**：真正起决定作用的是**暗部过滤 + 饱和度加权**；背景一旦被滤除，主体自然胜出，中心先验只是加速项。这说明**没有必要为了"主体定位"引入显著性模型**。
